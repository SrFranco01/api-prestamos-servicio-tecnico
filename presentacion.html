Garantías de Integridad y Transiciones Atómicas
14 Reglas (RN-01 a RN-14)
RN-07: Bloqueo Atómico de Celular
Al crearse el préstamo, el celular pasa a disponible = 0 en la misma transacción. No hay ventana de vulnerabilidad.
RN-12: Aislamiento Ante Rechazo
Si el celular está ocupado, la API frena la operación (CA-02), hace rollback y ningún dato existente es alterado.
RN-11: Liberación en Devolución
Al devolver el equipo, el préstamo pasa a DEVUELTO y el celular vuelve a disponible = 1 inmediatamente.
MOTOR DE PERSISTENCIA // TRANSACCIONALIDAD ACID

Persistencia, Motor Elegido y Esquema Relacional

¿Qué Motor Elegimos y Por Qué?
SQLite 3 Relacional

Para garantizar la robustez que exige QA, seleccionamos SQLite 3 nativo con capacidades transaccionales completas y camino directo hacia PostgreSQL:

1. Transacciones ACID Estrictas: Permite envolver el registro de préstamo en BEGIN TRANSACTION ... COMMIT, eliminando de raíz las condiciones de carrera (Race Conditions).
2. Integridad Referencial Forzada: Con PRAGMA foreign_keys = ON, la base de datos rechaza a nivel de motor cualquier intento de registrar un préstamo huérfano.
3. Cero Credenciales Expuestas: Cumplimiento estricto de la directriz de seguridad del docente: no hay passwords en repositorios ni puertos abiertos a internet.
Esquema DDL y Persistencia
DDL Schema
schema.sql (SQLite 3 DDL)
PRAGMA foreign_keys = ON; CREATE TABLE clientes ( id_cliente TEXT PRIMARY KEY, nombre TEXT NOT NULL, es_elegible INTEGER NOT NULL CHECK(es_elegible IN (0,1)) ); CREATE TABLE celulares ( id_celular TEXT PRIMARY KEY, modelo TEXT NOT NULL, disponible INTEGER NOT NULL CHECK(disponible IN (0,1)) ); CREATE TABLE prestamos ( id_prestamo TEXT PRIMARY KEY, id_cliente TEXT REFERENCES clientes(id_cliente), id_orden TEXT REFERENCES ordenes(id_orden), id_celular TEXT REFERENCES celulares(id_celular), estado TEXT CHECK(estado IN ('ACTIVO', 'DEVUELTO')) );
⚡ Estrategia de Consulta: Búsqueda indexada por estado = 'ACTIVO' para responder en <2ms las consultas de monitoreo en taller.

💡 CRITERIO DE SEMÁNTICA HTTP: RFC 9110 HTTP Semantics Compliance

Elegimos POST para creación (201 Created), GET idempotente para lecturas sin mutación de estado, y PATCH para la devolución porque mutamos parcialmente el estado del préstamo (`DEVUELTO`) y liberamos el recurso asignado sin destruir la entidad.
